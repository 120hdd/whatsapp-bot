راهنمای فارسی برای اجرای امن روی ویندوز، استقرار روی Ubuntu Server، شناخت صف و وضعیت‌ها، خواندن لاگ‌های JSON و رفع خطاهای متداول.

پیش از شروع

این پروژه دقیقاً چه کاری انجام می‌دهد؟

SajadBot WhatsApp یک سرویس تک‌اکانته برای ارسال کنترل‌شده به گروه‌های تأییدشده است. درخواست‌ها ابتدا در SQLite ثبت می‌شوند و Worker آن‌ها را با فاصلهٔ امن، retry محدود و گزارش حسابرسی پردازش می‌کند.

هشدار مهمBaileys یک کلاینت غیررسمی برای WhatsApp Web است و WhatsApp Business/Cloud API نیست. تغییر پروتکل یا محدودیت حساب ممکن است بدون اطلاع قبلی رخ دهد. پروژه ابزار scraping، دورزدن محدودیت یا ارسال انبوه به افراد ناشناس نیست.

ایمنی مقصد

هویت مقصد با JID ثابت ذخیره می‌شود. گروه تازه‌کشف‌شده به‌صورت پیش‌فرض غیرفعال است و باید صریحاً allow شود.

تحویل پایدار

صف، audit، auth و وضعیت‌ها در SQLite با WAL نگهداری می‌شوند. خاموش‌شدن برنامه باعث حذف jobها نمی‌شود.

جلوگیری از تکرار

محتوا، مقصد، زمان‌بندی و هش رسانه مبنای idempotency هستند؛ درخواست مشابه فعال یا تحویل‌شده دوباره ساخته نمی‌شود مگر با --force.

ارسال نامطمئن

اگر برنامه وسط حالت PROCESSING متوقف شود، job به REVIEW_REQUIRED می‌رود و خودکار دوباره ارسال نمی‌شود.

۴) اجرای Worker

# اجرای توسعه‌ای در foreground
npm run dev -- start

# اجرای خروجی buildشده

پنجرهٔ Worker را باز نگه دارید. فقط یک نمونه می‌تواند با یک LOCK_PATH اجرا شود. برای Task Scheduler ابتدا login را تعاملی انجام دهید، سپس:

  • Program: C:\Program Files\nodejs\node.exe
  • Arguments: C:\path\to\whatsappBot\dist\cli\index.js --config C:\path\to\whatsappBot\.env start
  • Start in: C:\path\to\whatsappBot

گزینهٔ restart on failure و اجرای «هنگام شروع سیستم» را فقط بعد از موفقیت اجرای دستی فعال کنید. مسیر پروژه و .env را با ACL ویندوز فقط در دسترس حساب سرویس قرار دهید.

خطاهای محتمل و راه‌حل

AUTH_REQUIRED / LOGGED_OUT

credential وجود ندارد یا مجوز Linked device باطل شده است. jobها پاک نمی‌شوند.

# سرور
sudo systemctl stop sajadbot-whatsapp
sudo -u sajadbot-wa sajadbot-wa --config /etc/sajadbot-whatsapp/bot.env auth login
sudo systemctl start sajadbot-whatsapp

# ویندوز
npm run dev -- auth login
npm run dev -- start
REVIEW_REQUIRED / stale_jobs_require_review

برنامه در حالی متوقف شده که job در حال پردازش بوده و نتیجهٔ remote نامشخص است. پیام را در گروه بررسی کنید؛ سپس queue mark-sent، queue retry یا queue cancel را آگاهانه اجرا کنید.

Unknown destination یا گروه در فهرست نیست

ابتدا groups refresh و بعد groups list را اجرا کنید. برای راحتی alias بسازید و مقصد را صریحاً allow کنید. عضویت حساب در گروه را نیز بررسی کنید.

Disabled / unsendable / PERMISSION_ERROR / DESTINATION_ERROR

احتمالاً گروه allow نشده، حساب دیگر عضو نیست، محدودیت ارسال دارد یا مقصد حذف شده است. یک خطای دائمی مقصد می‌تواند آن را unsendable کند. عضویت و مجوز را در WhatsApp اصلاح کنید، سپس refresh و بازبینی اپراتوری انجام دهید.

RATE_LIMITED

job به WAITING_RATE_LIMIT می‌رود و معمولاً پس از حداقل ۶۰ ثانیه یا زمان اعلام‌شده retry می‌شود. daemon را پیاپی restart نکنید و SEND_INTERVAL_MS را بی‌دلیل کاهش ندهید.

TEMPORARY_NETWORK / CONNECTION_CLOSED / whatsapp_reconnect_failed

شبکه، DNS، proxy/firewall و ساعت سیستم را بررسی کنید. اتصال با backoff نمایی تا RETRY_MAX_MS دوباره برقرار می‌شود. خطاهای ECONNRESET، ETIMEDOUT و وضعیت‌های 408/5xx گذرا طبقه‌بندی می‌شوند.

MEDIA_ERROR یا فایل staged پیدا نمی‌شود

وجود فایل در MEDIA_DIR، permission و اندازه نسبت به MAX_MEDIA_BYTES را بررسی کنید. Worker عمداً به مسیر اصلی فایل برنمی‌گردد؛ فایل staged را از backup بازیابی یا job را لغو و دوباره ایجاد کنید.

Database locked / Already running

فقط یک daemon با یک lock مجاز است. در Linux از systemctl status و در ویندوز از Task Manager استفاده کنید. lock را وقتی PID آن هنوز فعال است حذف نکنید. اگر هیچ پردازشی فعال نیست، ابتدا backup بگیرید و سپس lock stale را بررسی کنید.

Invalid configuration / Unknown TIMEZONE

مقادیر .env با Zod اعتبارسنجی می‌شوند. boolean فقط مقادیری مثل true/false/1/0/yes/no می‌پذیرد؛ RETRY_MAX_MS باید از base کمتر نباشد و timezone باید نام IANA معتبر مثل Asia/Tehran باشد.

زمان‌بندی بدون offset رد می‌شود

2026-09-21T12:30:00 مبهم و نامعتبر است. از 2026-09-21T12:30:00+03:30 یا زمان UTC مانند 2026-09-21T09:00:00Z استفاده کنید.

QR نمایش داده نمی‌شود

auth login را مستقیم در ترمینال تعاملی اجرا کنید، نه داخل systemd یا Task Scheduler. اندازهٔ ترمینال را بزرگ کنید. برای مسیر جایگزین از --pairing-phone استفاده کنید.

نصب better-sqlite3 شکست می‌خورد

نسخهٔ Node و معماری سیستم را بررسی کنید. اگر binary آماده موجود نیست، در Ubuntu ابزارهای build و در Windows ابزارهای C++ Build Tools مورد نیاز است. سپس node_modules ناسازگار را جابه‌جا/حذف و npm ci را دوباره اجرا کنید.

Protocol breakage پس از تغییر Baileys

dependency پروژه exact-pinned است. ابتدا به lockfile بررسی‌شده برگردید و تست‌های typecheck/lint/test و هر سه smoke test را اجرا کنید. ارتقای RC باید جداگانه و با مرور migration guide انجام شود.

تداوم سرویس

پشتیبان‌گیری، بازیابی و امنیت

برای backup سازگار، سرویس را متوقف کنید یا از مکانیزم online backup خود SQLite استفاده کنید. این سه مورد را با هم نگه دارید:

  • /var/lib/sajadbot-whatsapp/app.db — صف، audit، cache و auth
  • /var/lib/sajadbot-whatsapp/media — فایل‌های لازم برای jobهای ارسال‌نشده
  • /etc/sajadbot-whatsapp/bot.env — تنظیمات سرویس
فقط app.db زنده را کپی نکنید.هنگام اجرا، فایل‌های -wal و -shm ممکن است state ثبت‌شده داشته باشند. backup شامل auth عملاً امکان دسترسی به حساب را می‌دهد؛ آن را رمزنگاری و access-control کنید.

پس از restore در Linux مالکیت را به sajadbot-wa:sajadbot-wa برگردانید و permission فایل‌ها/دایرکتوری‌های حساس را به‌ترتیب 0600/0700 نگه دارید. سپس ابتدا health و بعد سرویس را start کنید.

تحویل نهایی

چک‌لیست قبل از ارسال واقعی

  1. ✓ نسخهٔ Node حداقل 20 و همهٔ تست‌ها موفق‌اند.
  2. ✓ مسیرهای database، media و lock پایدار و دارای permission محدودند.
  3. ✓ login تعاملی موفق و auth status برابر AVAILABLE است.
  4. ✓ گروه با JID درست refresh، alias و به‌صورت صریح allow شده است.
  5. ✓ سه smoke test و یک ارسال --dry-run موفق‌اند.
  6. ✓ status/health و مسیر مشاهدهٔ لاگ بررسی شده‌اند.
  7. ✓ backup رمزنگاری‌شده و روش restore آزمایش شده است.
  8. ✓ اپراتور فرق FAILED و REVIEW_REQUIRED را می‌داند.
